## 2. The one thing that is not done

**No physical cube has ever been connected.** Every solve in this session is simulated, replayed from a session file, or decoded from the vendor captures shipped with `smartcube-web-bluetooth`.

The reason is worth stating precisely, because an earlier version of this note got it wrong. The machine **does** have a working Bluetooth controller (`6C:7E:67:BE:26:75`, state On, chipset BCM_4388, GATT among its supported services). What it does not have is a cube: the only device it knows is a pair of AirPods, and no QiYi, GAN, Giiker, GoCube, MoYu or Tornado name appears anywhere in its Bluetooth inventory. A live scan settles it: driving Chrome's device chooser through the CDP `DeviceAccess` domain with `acceptAllDevices` found **no BLE device advertising in range at all**. The adapter works, `navigator.bluetooth.getAvailability()` returns true, the scan path works — there is no cube here. The blocker is the physical object and nothing else.

The handoff to close it, in the product itself:

0. Open the app on `http://127.0.0.1:5173` in desktop Chrome, or on an https origin. **A plain LAN address such as `http://192.168.x.x:5173` cannot pair** — Web Bluetooth does not exist on an insecure origin, and the app now says so instead of failing silently.
1. Open Live Solve, enter the cube MAC if the cube needs one (it is remembered), tick `Show all devices` if the cube is not offered.
2. `Connect cube`, then `Run connection self-test`.
3. Turn the cube, do one solve, and one disconnect/reconnect.
4. `Export device session` and hand over the JSON — **also on failure**, because the file carries the advertised name, capabilities, packets and the exact error.
5. Replay it with `Replay session file`; a session that carries its scramble reproduces the whole capture, analysis included.

## 4. Known gaps

1. Physical hardware — see §2. Nothing in the repository has been produced by a paired cube; the app labels every capture `simulator`, `replayed session` or `cube` so this can never be misread.
2. Route comparison for OLL/PLL is against the shipped algorithm for the case, not a proven optimum; F2L/cross comparisons are true optima.
3. Coaching thresholds are absolute, not personal percentiles, contrary to `docs/product-spec.md`.
4. Byte-exact GATT replay through the application's own connect path works for six of the eight shipped captures; QiYi Tornado and GAN gen2 fail inside the strict mock while their drivers decode both captures correctly, so that is harness fidelity rather than a product defect.
5. No real solve corpus, so segmentation is validated against exactly one human reconstruction.
