# Dogfood pass — 2026-08-03

Driven in a real browser at `http://127.0.0.1:5173`, session `coach-dogfood`, input via the simulator source. Each finding records the control driven, the observed value, the root cause, and the fix.

## D1 — TPS was computed over a different window than the execution column it sits beside

**Control:** Solves → `Rolling baselines and stage trends` table, after three captured solves.
**Observed:** `F2L 1 — recognition 809 ms, execution 0 ms, TPS 1.90`. A stage cannot execute in zero milliseconds and still have a turn rate.
**Root cause:** `src/domain/reconstruction.ts` computed `executionMs` as `lastMove - firstMove` but `tps` as `moves / (lastMove - previousStageEnd)` — the second window includes recognition. A single-move stage therefore printed `0 ms` execution beside a fabricated turn rate.
**Fix:** both branches (normal stages and the AUF stage) now divide by `executionMs`. A stage whose execution window is not measurable reports `tps: 0` rather than inventing a rate.
**Downstream:** `stageTrends` averaged those zeros into the displayed rate, dragging every stage average down. It now averages only measurable stages and returns `undefined` when none is measurable; `HistoryProgress` renders `—`. `LiveSolve` no longer emits a `stage_tps` metric sample for an unmeasurable stage, so coaching baselines are not polluted.
**Verified:** fresh capture `#e102de89` — `Cross exec 1176 ms tps 4.25`, `F2L 1 exec 0 tps 0`; `src/domain/cfopSimulation.test.ts` pins `tps === moveCount / executionMs` for every measurable stage and `0` otherwise.

## D2 — Phantom stages containing no turns

**Control:** same table, plus per-solve stage records read from IndexedDB.
**Observed:** capture `#298418b0` contained `F2L 2 — 0 moves, 0 ms execution, 698 ms recognition`. A stage the solver never executed was charging 698 ms of recognition to coaching metrics.
**Root cause:** stage completion is evaluated against a rotation-invariant frame, so a pure `y` rotation can change which slot counts as next and satisfy the next predicate. The segmenter emitted a stage whose entire segment was rotations.
**Fix:** when a segment contains no turns the stage record is skipped, its rotations fold into the following stage, and slot bookkeeping still advances so later stages are labelled correctly.
**Verified:** capture `#e102de89` has no zero-move stage; `src/domain/cfopSimulation.test.ts` asserts across four seeds that no emitted stage has `moveCount === 0`.

## D3 — Rejected state request killed the flow (found via the vendor matrix, fixed the same day)

**Root cause:** `createScramble` and `resyncFacelets` awaited `requestState()` unguarded, so a rejection became an unhandled rejection and the scramble was never set while the connection stayed live and healthy.
**Fix:** `requestLiveState()` catches, surfaces `Sticker request failed: … · connection kept`, and preserves the connection.

## Rejected change — slot attribution by "slots that newly completed"

F2L slots are credited to the first slot in `progress.slots` not already recorded. That looked wrong: on a simulated solve, `F2L 2` was credited a slot whose cross-plus-pair optimum was already `0`, meaning the pair was solved before that stage began. Changing attribution to "only slots that newly appeared at this boundary" fixed the simulated case and **broke the ground truth**: on the human reconstruction `public/reco/13444.json`, `F2L 4` lost its slot entirely, because at the previous boundary two slots read as solved at once. The reconstruction is the authority, so the change was reverted and the original attribution kept.

**Still open:** on some solves a pair stage carries a slot whose optimum at stage entry is `0`. `pairOptimum` already suppresses the comparison in that case, so no wrong number is displayed — but the stage boundary itself is probably early. Resolving it needs more than one human reconstruction to check against; a real solve corpus is the blocker, not the algorithm.

## D4 — Dead controls that never say why

**Control:** Live Solve with a cube connected (QiYi fixture through the real connect path) → `Build solver continuation`, and Train → `Recognized`.
**Observed:** both controls sat disabled or inert with no explanation. Driving them in the browser, I read both as broken before checking the code; a user has no code to check.
**Root cause:** `guidanceReady` gates the continuation on capture status plus verified stickers, and `Recognized` only greys itself out. Neither surfaced its own precondition.
**Fix:** the continuation now states `Apply the scramble on the cube first…` or `Waiting for a verified sticker snapshot…` depending on which precondition is unmet; the trainer confirms `Recognition captured at N.NN s` and otherwise prompts `Press Recognized the moment you know the case`.
**Verified:** the trainer message is covered by `src/components/TrainerHub.test.tsx`. The continuation message was verified in the running browser on the connected path — a jsdom test for it depends on live scramble generation and was dropped rather than shipped flaky.

## Harness note

Closing an `agent-browser` session discards its profile, and with it IndexedDB. Solve history captured before a session close is gone on reopen. That is the harness, not the application — do not read it as a persistence defect.
